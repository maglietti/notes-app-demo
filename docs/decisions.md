# Decisions

A running log of the choices behind this demo and why, so they do not have to be
re-derived. Newest sections last. Each entry is the decision and the reason, not
the whole debate.

## Stack

- **Connection: REST (consumed), native as the default runtime.** The app is
  designed as a client of the MariaDB REST Service the agent builds, because that
  tier is the talk's subject. It ships a native-connector fallback and defaults to
  it, because serving REST over HTTP needs a router that is out of scope. See the
  router entry below.
- **Interface: TUI.** The whole demo lives in a terminal over MCP and SQL. A TUI
  keeps the payoff in the same register, with no browser, build step or CORS, and
  starts instantly on a projector.
- **Language: Python + Textual.** Charm is a Go framework and falls outside the
  Python/Node constraint; Textual is the Python equivalent. Python also matches the
  surrounding plugin tooling. Node + Ink and a React web app were the runners-up.
- **HTTP client: httpx, not requests.** Textual runs on asyncio, and a blocking
  `requests` call would freeze the UI mid-render. httpx mirrors the `requests` API,
  so little familiarity is lost.

## Repository structure

- **The app lives at the repository root** as a `notes_app` package, the Pythonic
  layout. Working artifacts live in `working/`; inputs the agent reads live in
  `docs/` and `research/`.
- **`bin/notes-app` is a committed launcher at the root.** It runs
  `python -m notes_app` and survives a `working/` reset, so the stage command never
  changes. `bin/` holds only the launcher, never the app source.
- **The sandbox data directory is `working/sandbox`**, so everything the demo
  generates stays inside the repository. `working/` is gitignored (a global ignore
  already excludes it), so none of it is committed.

## Schema and data

- **The schema is designed live on stage (authentic beat), and the reference is a
  check, not an input.** Prompt 1 is the short original prompt; the agent designs
  the schema. `research/notes_app.sql` is the oracle it is compared against, never
  fed into the prompt. Drift on a free run is a finding, not a failure.
- **The canonical schema is frozen from an agent run.** `research/notes_app.sql` is
  the exact schema the agent designed, captured from `SHOW CREATE TABLE`. This makes
  the on-stage design and the app's schema the same artifact, and it is what native
  mode binds to (primary key `id`, generated `notebook.default_flag`,
  `note_tag.added_at`, no password field).
- **Test data is a committed fixture loaded as a direct step, not generated by a
  prompt.** `research/synthetic_data.sql` is self-contained and idempotent (creates
  the account and notebooks, guards every insert, references the account by email).
  Loading it is deterministic and demo-safe; asking the agent to generate data would
  be variant-tolerant but non-deterministic, which is the wrong trade for a demo.
  The schema is pinned, so the deterministic load is also safe.

## REST tier

- **The REST tier is the demo, not scaffolding for the app.** The talk is about the
  agent building an API tier, so creating the endpoints is the payload, not setup.
  They exist independent of any client. It is also the strongest evidence for the
  skills thesis: REST Service DDL (the session-state rule, `@UNNEST`, the CRUD flags)
  is the most niche, least-trained grammar in the run, the place a model is most
  confidently wrong without a skill.
- **The app does not consume the endpoints, and is not proof of the tier.** Native
  mode talks straight to the tables. The app's original job was to validate the API
  by consuming it; native mode removed that role, so the app is now a usable client
  on the same schema, nothing more. What the router's absence orphaned is the
  app-as-proof, not the REST creation.
- **Demo endpoints are created without `AUTHENTICATION REQUIRED`**, so a client can
  read them without an auth app. Production would add an MRS auth app, a REST role
  and a test user.
- **The metadata is the proof, and it proves defined, not served.** `SHOW REST` and
  `SHOW CREATE REST VIEW` confirm the agent produced correct REST grammar. They do
  not prove an endpoint answers over HTTP, which needs the router. State this
  precisely on stage ("the API definition is here; serving it is a router away")
  rather than claiming the endpoints answer.

## Serving and the router

- **Skip the router for the talk; native mode is the demo path.** Serving
  `/notesApp` over HTTP is a MySQL-Router-family binary (MariaDB's "REST Daemon")
  bootstrapped against the metadata on port 8443. The `mariadb-shell-plugins` only
  manage the metadata and register routers; they do not bundle or start one.
- **Caddy was rejected.** It is a reverse proxy with no MRS awareness. It cannot
  read `mysql_rest_service_metadata` or translate HTTP into the SQL that builds a
  response. Its only possible role is TLS in front of a real router, which a local
  demo does not need.
- **REST mode stays documented, not built.** If it is wanted post-talk, the closer
  is a real router plus a `RestDataSource` TLS tweak for the dev certificate. The
  open unknown is which router binary MariaDB ships as the REST Daemon and how to
  obtain it.

## Talk framing

- **The title stays unchanged.** It is locked in the published agenda, and it is
  accurate regardless: it claims the agent *builds* an API tier, which it does. The
  router only serves that tier, and serving was scoped out in the abstract from the
  start.
- **Do not present the native-mode app as running on the REST tier.** Native mode
  talks straight to the tables and bypasses `/notesApp`. Claiming otherwise is the
  one dishonest move to avoid.
- **State the router boundary as a one-sentence teaching beat.** The metadata proves
  the tier is real; the app is a client against the same schema; serving over HTTP
  is a separate piece not stood up live. Naming that boundary models the talk's own
  thesis about knowing where the agent's competence stops.

## Supporting decisions

- **The skills smoke test keys on MariaDB-only constructs, not the primary key
  type.** The `mariadb-create-table` skill picks the key by domain, so `UUID_v7()`
  is not a reliable tell. `CREATE OR REPLACE TABLE`, `utf8mb4`, system versioning
  and the rest are.
- **The blocked mass delete is kept as a talking point.**
  `research/agent-security-note.md` records the incident: the database would have run
  the delete, the account had the privilege, and the harness classifier vetoed it
  above the grants.
