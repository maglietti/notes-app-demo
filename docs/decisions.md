# Decisions

A running log of the choices behind this demo and why, so they do not have to be re-derived. Newest sections last. Each entry is the decision and the reason, not the whole debate.

## Stack

- **Connection: REST (consumed), native as the default runtime.** The app is designed as a client of the MariaDB REST Service the agent builds, because that tier is the talk's subject. It ships a native-connector fallback and defaults to it, because serving REST over HTTP needs a router that is out of scope. See the router entry below.
- **Interface: TUI.** The whole demo lives in a terminal over MCP and SQL, so a TUI keeps the payoff in the same register, with no browser, build step or CORS, and it starts instantly on a projector.
- **Language: Python + Textual.** Charm is a Go framework and falls outside the Python or Node constraint, while Textual is the Python equivalent and matches the surrounding plugin tooling. Node with Ink, and a React web app, were the runners-up.
- **HTTP client: httpx, not requests.** Textual runs on asyncio, and a blocking `requests` call would freeze the UI mid-render. httpx mirrors the `requests` API, so little familiarity is lost.

## Repository structure

- **The repository tracks the instructions, not the app.** It holds the runbook, the prompts, the design, the canonical schema and the seed. Everything the prompts or the agent produce is gitignored: the generated `notes_app` package, `pyproject.toml`, `uv.lock`, `.env`, `.env.example`, the `.venv`, and everything under `working/`. A run never dirties the repo, and `git clean -fdx` returns it to a pristine, re-runnable state with no residue from a previous generation. That is the point, since the app regenerates from the instructions in minutes and does not belong in version control.
- **The app is generated at the repository root** as a `notes_app` package, the Pythonic layout, but it is ignored rather than committed. Inputs the agent reads live in `docs/` and `research/`, and working artifacts land in `working/`.
- **`bin/notes-app` is a committed launcher at the root.** It runs `python -m notes_app` against whatever the agent generates, and it survives a reset, so the stage command never changes. It is instructions and tooling rather than app source, which is why it is the one root-level runtime file that is tracked.
- **The sandbox data directory is `working/sandbox`**, so it is covered by the `working/` ignore and cleaned with everything else.

## Schema and data

- **Act one turns the PRD's data model into DDL, and the reference stays out of the prompt.** Prompt 1 points the agent at section 4 of `docs/notes_app-prd.md`, which specifies the schema column for column, so the result is predictable from run to run and matches the names the app binds to. Prompt 1 does not read or compare against `research/notes_app.sql`. The checks are the server accepting the DDL and the fixture loading into it, and a schema fix the fixture forces is a finding rather than a failure. This replaced a free design from a one-line prompt, which drifted on names the app and the REST views depend on, such as `user` for `account`. Section 4 describes what each column must do rather than the syntax that does it, so the MariaDB idioms in a generated schema stay the agent's choice and act one still shows the skills at work.
- **The PRD does not link the reference schema.** The agent reads the PRD, so a link to `research/notes_app.sql` or its ER diagram would put the answer key one hop from the agent's input and undo the rule above. The README and this log still point at both for people.
- **The canonical schema is frozen from an agent run.** `research/notes_app.sql` is the exact schema the agent designed, captured from `SHOW CREATE TABLE`. This makes the on-stage design and the app's schema the same artifact, and it is what native mode binds to (primary key `id`, generated `notebook.default_flag`, `note_tag.added_at`, and no password field).
- **Test data is a committed fixture that Prompt 1 loads, not data the agent generates.** `research/synthetic_data.sql` is self-contained and idempotent, creating the account and notebooks, guarding every insert, and referencing the account by email. Loading it is deterministic and demo-safe, whereas asking the agent to generate data would be variant-tolerant but non-deterministic, the wrong trade for a demo. The fixture is also the data contract: when it fails to load, the agent fixes the schema and never edits the fixture.

## REST tier

- **The REST tier left the talk, and Prompt 3 stays in the repo.** The REST Service DDL (the session-state rule, `@UNNEST`, the CRUD flags) is the least-trained grammar in the run, which made it the strongest evidence for skills. It moved from the middle act to an optional third act to fit the clock, and on 2026-09-25 it left the stage entirely, replaced by the spec beat (see "Talk framing"). The app does not consume the endpoints, and the REST server expected in `mariadb-shell` is not ready yet, so a live act spent its time on caveats. A static slide of about 45 seconds shows the `SHOW REST VIEWS` output from an off-stage Prompt 3 run and states the boundary, so the title's promise still gets its honest sentence.
- **The app does not consume the endpoints, and is not proof of the tier.** Native mode talks straight to the tables, and the REST mode that Prompt 3 adds can only report that nothing is serving. The app's original job was to validate the API by consuming it, and native mode removed that role, so the app is now a usable client on the same schema, nothing more. What the router's absence orphaned is the app-as-proof, not the REST creation.
- **Demo endpoints are marked `AUTHENTICATION NOT REQUIRED`**, so a client can read them without an auth app. The clause must be explicit, because a view created without it defaults to `AUTHENTICATION REQUIRED`. Production would add an MRS auth app, a REST role and a test user.
- **The metadata is the proof, and it proves defined, not served.** `SHOW REST` and `SHOW CREATE REST VIEW` confirm what the metadata holds, but they do not prove an endpoint answers over HTTP, which needs the router. Nor is the metadata always what the DDL asked for: on mariadb-shell 26.9.3 the nested read-only flags on `/note` are dropped on the way in, so Prompt 3 reads the view back and reports the mismatch (PRD section 13). The cause is `plugins/mrs_plugin/lib/db_objects.py:762`, which saves each nested `object_reference` with the parent object's options (`obj.get("options")`) instead of its own. An `UPDATE` on `mysql_rest_service_metadata.object_reference` corrects the flags, but it bypasses the shell and is untested against a router, so the demo reports rather than patches. State this precisely on stage ("the API is defined in the metadata; the server that would serve it is not ready yet") rather than claiming the endpoints answer.

## Serving and the router

- **The REST server expected in `mariadb-shell` is not ready yet (2026-09-25).** Until it ships, nothing in the stack serves the metadata over HTTP, which is why the REST tier left the talk.
- **Skip the router for the talk; native mode is the demo path.** Serving `/notesApp` over HTTP is a MySQL-Router-family binary (MariaDB's "REST Daemon") bootstrapped against the metadata on port 8443. The `mariadb-shell-plugins` only manage the metadata and register routers, and they neither bundle nor start one.
- **Caddy was rejected.** It is a reverse proxy with no MRS awareness, so it cannot read `mysql_rest_service_metadata` or translate HTTP into the SQL that builds a response. Its only possible role is TLS in front of a real router, which a local demo does not need.
- **REST mode is built only by Prompt 3, and it cannot serve data without a server.** Prompt 3 adds `RestDataSource` and `NOTES_APP_MODE`, and REST mode shows the connection error and stays up. If live REST mode is wanted post-talk, the closer is a real router plus a `RestDataSource` TLS tweak for the dev certificate. The open unknown is which router binary MariaDB ships as the REST Daemon, and how to obtain it.

## The PRD as a specification

- **The PRD is agent input only, so it holds requirements, not talk notes or rationale.** It started as the talk's product doc and became the contract the agent builds to. Version 2.0 removed what an agent should not read as instruction: the talk framing, the stage risks, the runbook (the README carries it), and the reasons behind the stack (this log carries them). Talk concerns live in `talk/`.
- **One spec file, not a Spec Kit layout.** A separate constitution, plan, and tasks file is more ceremony than a one-app demo needs. The three prompts already act as the task list, and PRD section 12 gives the build order. An auto-loaded `AGENTS.md` or `CLAUDE.md` was rejected too, because it would blur the claim that the MariaDB idioms come from the skills.
- **The acceptance criteria live in the spec.** PRD section 11 holds the checks for each prompt (`AC-D`, `AC-A`, `AC-R`), and each prompt ends by asking the agent to report against them. Before this, the checks lived only in the prompts' "What to check" notes, which the agent never saw, and in four copies that drifted.
- **Requirements carry IDs, and the prompts stay thin.** Packaging, configuration, and the REST view definitions moved from Prompts 2 and 3 into the PRD (`PK-`, `CF-`, `API-`). The prompts keep the slice to build, where to write, the order, and the few hard constraints the talk calls out by name: never edit the fixture, run the REST DDL one statement at a time, and report the dropped flags without patching the metadata. Section numbers 4 to 9, 12, and 13 kept their numbers, so references to them still hold.

## Talk framing

- **Spec-driven development replaces the REST act (2026-09-25).** It extends the thesis rather than adding a topic: skills stop the agent guessing about MariaDB, a spec stops it guessing about the app, and acceptance criteria stop it guessing when it is done. It is how the presenter works with an agent day to day, it transfers to any stack, and the acts prove it, since each ends in an acceptance-criteria report. It gets a two-minute beat before act one, built from evidence: the one-line prompt that drifted on names, real lines from the PRD, and the reports. It stays a practice, not a methodology pitch.
- **The title stays unchanged.** It is locked in the published agenda, and it is accurate regardless, since it claims the agent *builds* an API tier, which the off-stage Prompt 3 run does. The static REST slide keeps that promise in about 45 seconds. Serving the tier was scoped out of the abstract from the start.
- **Do not present the native-mode app as running on the REST tier.** Native mode talks straight to the tables and bypasses `/notesApp`, so claiming otherwise is the one dishonest move to avoid.
- **State the router boundary as a one-sentence teaching beat.** The metadata proves the tier is defined, the app is a client against the same schema, and the server that would serve it over HTTP is not ready yet. Naming that boundary models the talk's own thesis about knowing where the agent's competence stops.
- **The public abstract stays as written; the spoken claim is corrected.** The locked abstract and session page say the run "queries the metadata to confirm the endpoints answer," which overstates it. The published copy is locked in the agenda and stays, but the talk track never says the endpoints answer. On stage the claim is that the metadata confirms the endpoints are defined, and the server that would serve them is not ready yet.

## Supporting decisions

- **The skills smoke test keys on MariaDB-only constructs, not the primary key type.** The `mariadb-create-table` skill picks the key by domain, so `UUID_v7()` is not a reliable tell, whereas `CREATE OR REPLACE TABLE`, `utf8mb4`, system versioning and the rest are.
- **The blocked mass delete is kept as a talking point.** `research/agent-security-note.md` records the incident, where the database would have run the delete, the account had the privilege, and the harness classifier vetoed it above the grants.
