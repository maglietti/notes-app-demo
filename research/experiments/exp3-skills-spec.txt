  Tables
  - All five tables: account, notebook, tag, note and note_tag. Their columns
    match the INSERT column lists in synthetic_data.sql exactly.
  - Keys: every table except note_tag uses a UUID primary key with DEFAULT 
    UUID_v7(). The sample data looks up ids by email or name and never
    hard-codes them, so these defaults work. note_tag uses a composite primary
    key (note_id, tag_id).
  - Status: note.status is ENUM('active','archived','trashed') and defaults to
    active. is_pinned and is_default are BOOLEAN. body is MEDIUMTEXT.
  - Timestamps: created_at defaults to the insert time. updated_at also has ON 
    UPDATE CURRENT_TIMESTAMP, so it changes on any update.

  Integrity
  - Uniqueness: account.email is unique, and so is the name per account for both
    notebooks and tags. This also makes the sample data's NOT EXISTS re-run
    guards reliable.
  - One default notebook per account: a stored generated column holds account_id
    only when is_default is true, and a unique key sits on that column.
  - Same owner: a composite FK from note(notebook_id, account_id) to
    notebook(id, account_id) stops a note from landing in another account's
    notebook.
  - Deletes:
    - Deleting a note or a tag cascades to its note_tag rows, so emptying the
      trash is a plain DELETE.
    - Deleting a notebook that still has notes is blocked.
    - Deleting an account cascades to its notebooks and tags.

  Indexes
  - note(notebook_id, status, is_pinned DESC, updated_at DESC) handles the
    notebook note list and the per-notebook counts.
  - note(account_id, status, updated_at DESC) handles the trash and archive
    views.
  - note_tag(tag_id, note_id) is ready for the planned filter by tag.

  Decisions for you
  - "Newest first" sort: I sorted on updated_at. Because it updates on any
    change, pinning or archiving a note moves it to the top. If you want
    creation order, switch the index to created_at, or have the app set
    updated_at itself.
  - Titles: they are not unique, because the spec doesn't require it. The sample
    data does treat title as a per-account key for its re-run guard and tag
    links, and the 61 titles in the file are currently unique. Loading duplicate
    titles would create extra tag links.
  - Setting a new default notebook: the app must clear the old default and set
    the new one in one transaction.
  - Re-running the script: CREATE OR REPLACE TABLE drops the existing tables and
    their data each time.
  - Full-text search: I left out the FULLTEXT index, since the spec lists search
    as later.
